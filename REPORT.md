# DocLens: experiments, results and failures

Everything quoted here is produced by code and stored in [`doclens/eval/results/`](doclens/eval/results/). The tables are generated by
`python eval/render_tables.py` and pasted between the markers; the analysis underneath was written by reading the per-document rows in
those same files. If a number is not in a results file, it is not in this report.

## 1. Problem and setup

**Question.** Can a document pipeline turn Japanese and English business documents into structured JSON that a reader can trust, and
where exactly does it break? Four things are measured: how well different parsers read the page, how well an extractor fills a schema
from what was parsed, whether the evidence check and the arithmetic checks flag the values that are wrong, and what it costs in time.

**Data.** Synthetic Japanese invoices, generated by [`eval/synth/generate.py`](doclens/eval/synth/generate.py) with seed 0, so ground truth is exact.
12 invoices, each written twice: as a clean PDF with a text layer (rendered by Chromium) and as an image-only "scan" (rotation of ±2°,
blur, ink bleed, JPEG artifacts, a red 印 stamp over the issuer block). That is 24 documents, one page each.

| | |
|---|---|
| Layouts (rotated through the set) | **A** classic Japanese 請求書 with a ご請求金額 box and a right-hand header; **B** English labels (`INVOICE`, `Bill to`, `Subtotal`) with a two-column header; **C** a tax-rate column with mixed 10% and 8%, tax shown per rate |
| Dates | `2026/10/24`, `令和8年10月24日`, `２０２６年１０月２４日`, `R8.10.24` |
| Amounts | `¥1,234`, `1,234円`, full-width `￥１，２３４` |
| Line items | 2–11 per invoice; 12 rows maximum so one page always fits |
| Fields | invoice number, issue date, due date, issuer, recipient, subtotal, tax, total, line items (name, quantity, unit price, amount) |

Also generated, for the smaller experiments: 6 charts with exact values ([`eval/synth/charts.py`](doclens/eval/synth/charts.py)) and 2 PowerPoint
decks with known facts ([`eval/synth/decks.py`](doclens/eval/synth/decks.py)).
English and Bangla invoices (6 of each, [`eval/synth/intl.py`](doclens/eval/synth/intl.py)) are described in 4.11.
**Not used: real documents.** Redistributable real PDFs with hand-made labels were out of reach for this work; see Limitations.

**Hardware and models.** Recorded in each results file (`config.hardware`, `config.parser_version`, `config.llm`, `config.notes`). The
runs here used a 4-core CPU and no GPU. The extraction model was Qwen2.5-3B-Instruct (Q4_K_M) served by llama-cpp-python, temperature 0, output constrained
to the JSON schema. GPU configurations (VLM parsers, vLLM, quantisation, LoRA) are written as notebooks and are listed as "not run" in the tables.

**Metrics** ([`eval/metrics.py`](doclens/eval/metrics.py)). Values are compared after normalisation (NFKC, no whitespace, numbers as numbers), so `３，８００` equals `3,800`.

| Metric | Definition |
|---|---|
| Field F1 | Precision and recall over (field, value) pairs; a line-item row counts as one pair. Micro-averaged over documents. |
| Field accuracy | Exact match per field, macro-averaged over the 9 fields (the 8 header fields and `line_items`, which is right only if every row is). |
| Verified rate | Share of predicted values that pass the evidence check. |
| Wrong values flagged | Of the predicted values that are wrong, the share the evidence check marks `unverified` (the hallucination catch rate). |
| Right values flagged anyway | The false-alarm rate of the same check. |
| …caught by evidence or arithmetic | Of the documents with at least one wrong value, the share where the evidence check flagged a wrong value **or** an arithmetic check failed. |
| Table TEDS | Tree-edit-distance similarity of the parsed items table and the true one (insert/delete cost 1; renaming a cell costs the normalised Levenshtein distance of its text). A missing table scores 0. |
| Parse pages/s | Wall-clock pages per second for the parser alone. The first document is parsed once untimed, so model load is excluded. |
| End-to-end s/doc | Parse plus extraction. |
| Peak VRAM, $/1k pages | `torch.cuda.max_memory_allocated` (or `nvidia-smi` for a vLLM server) and `seconds per page × 1000 / 3600 × GPU_HOURLY_USD`. Only filled on a GPU, and the hourly price is an assumption written into the result. |

**The evidence check** ([`backend/extract.py`](doclens/backend/extract.py), [`backend/verify.py`](doclens/backend/verify.py)). The model returns each value as printed, the id of the element it is in and a quote. A field is
`verified` only if (1) the quote is found in the element (fuzzy match ≥ 0.9 after NFKC and whitespace removal), (2) the value appears in its quote,
and (3) the value appears in the element the quote was found in. Rule 3 exists because rule 1 accepts a quote with one digit changed:
in a test, a model "quoted" `1,200` against a real row that said `1,000`, and without rule 3 that passed.

## 4. Failure analysis

Figures referenced below are in [`docs/failures/`](docs/failures/); the first two are screenshots of the app showing real extractions.
"Cause" labels come from [`eval/failures.py`](doclens/eval/failures.py), which looks at what the parser actually produced; they say where to look, and every document is in the results files for checking.

### 4.1 Hallucination is rare; the common wrong value is a real value in the wrong place

Of the failures the classifier found in the Docling + Qwen2.5-3B run, only 3 were values that appear nowhere in the parsed text (1 clean, 2 scanned).
Far more were real text assigned to the wrong field. The evidence check is built for the first kind and is blind to the second.

**Party roles (issuer / recipient).** On clean pages Docling + Qwen got every invoice number, date, amount and line-item set right (100% each), and
`issuer` and `recipient` right only 17% and 25% of the time; role confusion is the largest single cause in the table above.
In [`role-confusion.png`](docs/failures/role-confusion.png) the Issuer field is green (✓ verified), its quote is real, and the highlighted line is the addressee (`有限会社吉田通信 御中`).
Hypothesis: "who sent this" is a reading task, not a copying task, and the prompt names the fields only by label (請求元 / 御中), so a 3B model leans on position.
Fix to try: describe the roles by their evidence (the issuer has the address, TEL and bank details; the recipient is followed by 御中 or 様), check that the recipient's quote contains 御中/様 and the issuer's does not, or use a larger model.
No document in this run had every field right (0 of 24) because of this one pair.

### 4.2 Table structure

With the PDF text layer, the table is flat text. Item names that contain numbers (`LANケーブル 5m`, `ボールペン 黒 10本入`) are split at the digits and every column shifts
([`digits-in-names.png`](docs/failures/digits-in-names.png)): with Qwen2.5-3B `line_items` was right for 25% of clean invoices, 32 rows lost and 32 invented, while Docling's table structure
gave 100% on clean pages and a table score (TEDS) of 1.00 clean and 0.90 scanned.
The evidence check cannot see this: the shifted cells are real text with real quotes. The arithmetic checks can: 8 of the 12 text-layer + Qwen documents failed a check (quantity × unit price ≠ amount, or the row sum ≠ subtotal), and together with the evidence check they flagged a problem in 92% of the documents that had a wrong value.
Fix: keep the table structure (or send rows with explicit column separators) and keep the arithmetic checks.

### 4.3 OCR on scans

Docling's OCR (RapidOCR, default models) read scans with confusions that show up as "not in the parsed text": the true value is simply absent from the parser's output
([`stamp-and-ocr.png`](docs/failures/stamp-and-ocr.png)): the red 印 over the header turned `Amount` into `本`, `ペン` became `ベン`, `張` became a simplified-Chinese variant, and `12,800` became `12,80 0`.
That cause accounts for 39 of the Docling + Qwen failures on scans, and Docling + rules scored 0.40 field F1 on scans against 0.95 on clean pages.
Tesseract (jpn + eng, 200 dpi) was worse still: 0.28 with the LLM on scans, and 0.38 on clean pages, because it OCRs the rendered page even when a text layer exists.
Fix to try: remove the seal (it is red) before OCR; send scanned pages to a VLM, which is what the router does; check that the seal does not overlap a table header.

### 4.4 Reading order

In layout B (two-column header) Docling returns the labels `Invoice No.`, `Date`, `Due` as separate elements, then the values, so a label and its value are no longer neighbours
([`reading-order.png`](docs/failures/reading-order.png)). The regex baseline loses these fields (12 "present, not extracted" on clean pages; its `invoice_number`, `issue_date`, `due_date` accuracy is 67% there); the LLM copes (100% on the same fields).
Fix: pair labels and values by geometry, or let the model see the page.

### 4.5 Normalisation

No failure in any run was attributed to normalisation, including `85, 448円`, `12,80 0`, full-width commas (`38，000`) and all four date styles: the normaliser (55 test cases) did its job.
It cannot repair a wrong OCR read (`12,80 0` normalises to 12800 only because the 0 survived).

### 4.6 What the evidence check does and does not measure

In the Docling + Qwen run the evidence check flagged 45% of the 67 wrong values and 28% of the 249 right ones; 46 of the 70 right-but-flagged values were line-item cells.
Two causes, both visible in [`model-fixed-the-ocr.png`](docs/failures/model-fixed-the-ocr.png):

- **Sloppy quotes.** The 3B model often quotes the header, the separator and a row, or skips a row between two it quotes; the fuzzy match then falls under 0.9 although the value is right.
- **Faithfulness, not truth.** On `scan-001` the OCR text said `出张技術料`; the model wrote the correct `出張技術料`. The value is true but is not what the parsed text says, so it is flagged. In the row above it, the model copied the OCR's `ボールベン` faithfully, so that wrong value passes.

So the check answers "is this value in the document as it was read?", which is the right question for catching a model that invents values, and the wrong one for catching a parser that misreads them.
Fixes: verify each cell on its own (a quote that is right for three cells should not condemn the fourth), cell-level boxes, a tolerance table for known OCR confusions.

### 4.7 The arithmetic checks

They are cheap and they catch what evidence cannot (4.2). They also produced one false alarm class that was found and fixed during this work: a mixed 10%/8% invoice whose extracted rows carried no tax rate failed the "10% or 8% of the subtotal" rule.
The rule now also accepts a tax between 8% and 10% of the subtotal when rows carry no rate, which cannot be pinned down further; the stored predictions were re-scored with `eval/rescore.py` and each file notes it. That change lowered "caught by evidence or arithmetic" for Docling + Qwen from 75% to 62.5%: the earlier figure included false alarms.

### 4.8 A small VLM as parser (sample of 6 documents)

Qwen2.5-VL-3B (zero-shot, "convert this page to Markdown", 110 dpi, CPU) took about 232 s per page, against 4.6 s for Docling on the same pages, and scored lower on the same six documents (0.66 clean, 0.64 scanned, against 0.85 and 0.82 for Docling with the same extractor).
It answered with an HTML document rather than Markdown (the parser now reads that). On all three scans it returned only the table (the title, invoice number, dates and both company names were missing, so those fields were "not in the parsed text"), and on a clean page it dropped the cells of the first table row and wrote the amount box as LaTeX.
Its table values were accurate where present, including full-width commas. Six documents say little about a 7B VLM on a GPU; this row exists to show the harness works end to end and that a prompt for page-level Markdown is not enough for a 3B model.

### 4.9 Chart → table (6 synthetic charts, Qwen2.5-VL-3B)

All six replies were valid JSON, and the mean relative error over the values it found was 4.0%, but only 67% of the true points were returned at all.
The misses are visible in the re-plots next to the originals ([`chart-05.png`](doclens/eval/results/charts/charts-qwen2.5-vl-3b/chart-05.png): the model resampled the x-axis, nine points at 2.5 steps instead of six real ones;
[`chart-01.png`](doclens/eval/results/charts/charts-qwen2.5-vl-3b/chart-01.png): a nearly identical re-plot). One grouped chart came back with empty point lists, another lost a category.
With 3 charts per group, the 8.1% (labelled) versus 1.3% (unlabelled) error is noise, not a finding.

### 4.10 The router

On the cheap signals alone it sent all 12 scanned pages to the VLM and none of the 12 clean pages (24/24 as the ground truth says; the reasons were the missing text layer on every scan and a "figure" on every scan, which was the seal).
That is a weak test: a scan has no text layer by construction. It says the plumbing and the signals work, not that the router saves GPU time; that comparison (Docling-only, VLM-only, router; accuracy against GPU seconds) is `--parser router` on a GPU and has not been run.

### 4.11 English and Bangla (6 invoices each)

The Japanese set came first, so supporting two more languages exposed what was Japan-specific. Changes: `backend/normalize_intl.py` (month-name dates, `$` and `৳` amounts, Bangla digits, lakh/crore grouping and words);
a tax-rate check that applies Japan's 10% / 8% only to documents containing Japanese; Bangla language detection; a Bangla OCR route; English and Bangla labels in the regex baseline; a language note in the LLM prompt.
Data: [`eval/synth/intl.py`](doclens/eval/synth/intl.py), clean text-layer PDFs with exact ground truth (English: USD, `From` / `Bill To`; Bangla: `৳` with Bangla digits and `12,34,567` grouping, `বিক্রেতা` / `ক্রেতা`), party blocks stacked vertically.
Results are in the "English and Bangla" table above; the cause table lists the runs as `en-…` and `bn-…`.

**English works, and the explicit labels removed the role confusion.** Qwen2.5-3B got F1 0.85 and made no issuer/recipient swaps at all (0 of 6 documents), against 17% / 25% accuracy on those fields in Japanese.
The difference is the layout: `From` and `Bill To` sit on their own lines. What it got wrong was line items (10 rows lost, 6 invented) and 3 copy-boundary errors.

**A Bangla text layer cannot be trusted, so Bangla pages are OCR'd.** From a Chromium-rendered PDF, the characters come out right but pdfium puts spaces inside words (`চা লা ন` for `চালান`) and returns overlapping duplicate boxes (`নম্ব`, `নম্বর`, `ম্বর`).
`parse_path` therefore sends any PDF whose first page has Bengali letters in its text layer to Tesseract (`ben+eng`), unless you chose a parser yourself. Legacy-font Bangla PDFs, which are common, are worse and were not tested.

**Table borders break Tesseract's Bengali model.** On the first Bangla page, headers and totals were read but the whole bordered table came back as noise; with the ruling lines painted out beforehand (`parse.strip_rules`), the same row read exactly (`এ৪ কাগজ (৫০০ শিট) ১৬ ১২,৫০০ ২,০০,০০০`).
Resolution (200 vs 300 dpi) and page-segmentation mode made no difference. OCR errors remain (`ফুড` read as `ফুভ`, `ট্রে` as `ট্রৈ`, `৳` as `ট` or `&`), and the arithmetic check caught one of them (a subtotal read as `9`).

**The model translated Bangla into Japanese.** The first Bangla LLM run returned item names in Japanese (`スタンド＆セットアップ`) and dates as `2026年8月26日`: the prompt's examples and field guide are Japanese and a 3B model followed them.
The evidence check did its job: those values were not in the document, so they were flagged (F1 0.43, 44% verified, 81% of wrong values flagged; 23 failures classed as hallucinated). Adding a one-line Bangla note to the prompt (only for Bangla documents; Japanese and English prompts are unchanged) raised F1 to 0.56 and the verified rate to 66%, and cut "hallucinated" from 23 to 2.
The first run is kept as `eval/results/intl/bn-tesseract-ben-qwen2.5-3b-before-language-note.json`.

**What is still weak.** Bangla with the 3B model (F1 0.56) is behind the regex baseline on the same OCR text (0.77), which reads fixed labels without understanding Bengali; row boundaries are the main loss (14 lost, 23 invented).
The English and Bangla labels in the regex baseline were written after looking at these two layouts, so its English 1.00 is an upper bound. Six synthetic, clean, single-column documents per language say nothing about scans, handwriting, legacy fonts or real invoices.

## 5. Recommended next steps

1. **Fix party roles first**: it is the whole gap between 0.88 and a perfect clean-page score for the LLM runs. Try the role description, the 御中/様 cross-check and a 7B model, and measure with the same harness.
2. **Run the GPU notebooks** ([`kaggle_arena.ipynb`](doclens/notebooks/kaggle_arena.ipynb), [`kaggle_lora.ipynb`](doclens/notebooks/kaggle_lora.ipynb)): Qwen2.5-VL-7B and PaddleOCR-VL as parsers, the router experiment with GPU seconds, FP16 vs 4-bit, and the LoRA fine-tune. The *not run* rows in the tables are the checklist.
3. **Verify per cell, not per quote** and draw cell-level boxes, so that one sloppy quote stops condemning correct values and a click lands on the cell.
4. **Add a real-document slice**: redistributable Japanese and English PDFs with hand-labelled fields. Everything above is synthetic; the rules baseline in particular was written against these layouts.
5. **Treat scans properly**: seal removal before OCR, and compare against a layout-aware OCR pipeline.
6. **Read PPTX charts**: render the slide and send the chart to the chart reader (F6); today they are figures without values.
